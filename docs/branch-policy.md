# 브랜치 및 상설 워크트리 운영 정책

이 문서는 웹 저장소 `kimjeon-il/Pando`와 앱 저장소 `kimjeon-il/PandoEditor`에 공통으로 적용한다. 각 저장소의 루트 `AGENTS.md`에는 실행에 필요한 핵심 규칙을 두고, 이 문서에는 상세 절차를 둔다. **GitHub 브랜치와 로컬 워크트리는 서로 다른 개념**이며, 문서 변경만으로 로컬 워크트리가 생성되지는 않는다.

## 1. 유지할 브랜치

| 브랜치 | 책임 |
| --- | --- |
| `main` | 검증되어 승인받은 안정 통합본 |
| `work/ui` | 화면·패널·툴바·대화상자·UI/UX |
| `work/objects` | 국가·하위 행정단위·영토 객체, 관계·계보·기간·저장 모델 |
| `work/gis` | GIS 데이터·역사적 육상 국경·해안선·지리 검증·자료 조사 |
| `work/places` | 도시·취락·지명 자료·다국어 표기·지명 표시 |

- 기본 원칙은 **기존 `work/*` 브랜치 재사용**이다. 작업할 때마다 `codex/*`, `feature/*` 등을 새로 만들지 않는다.
- 브랜치는 파일 경로별 배타적 소유권이 아니라 **주요 작업 목적별 구분**이다. 둘 이상의 영역에 걸친 작업은 주된 목적에 해당하는 브랜치에서 수행하고, 교차 영향과 검증 범위를 명시한다.
- 웹과 앱은 **같은 브랜치 이름을 사용하지만 독립적인 Git 저장소**다. 같은 이름이라고 코드·커밋·기능이 동기화되었다고 간주하지 않는다.
- 예외적인 실험·릴리스 격리·충돌 회피용 임시 브랜치가 꼭 필요하면 이유와 종료 기준을 제시하고 사용자 승인 후 생성한다. 승인 없이 상설 브랜치를 대체하지 않는다.

## 2. 로컬 워크트리: 분야별 상설·재사용

로컬 개발 시 웹과 앱에서 각각 4개의 `work/*` 브랜치에 대응하는 **고정 작업 디렉터리**를 사용한다. 필요한 분야를 처음 작업할 때만 한 번 생성하고 이후 계속 재사용한다. 매 작업마다 신규 워크트리를 만들고 삭제하는 패턴을 사용하지 않는다.

디렉터리 배치 예시(실제 경로는 사용자 환경에 맞춘다):

```text
workspace/
  Pando/                     # 웹 저장소, main
  PandoEditor/               # 앱 저장소, main
  worktrees/
    web/
      ui/                    # Pando: work/ui
      objects/               # Pando: work/objects
      gis/                   # Pando: work/gis
      places/                # Pando: work/places
    app/
      ui/                    # PandoEditor: work/ui
      objects/               # PandoEditor: work/objects
      gis/                   # PandoEditor: work/gis
      places/                # PandoEditor: work/places
```

- 위 경로는 **예시일 뿐**이며 기존 로컬 경로·워크트리를 옮기거나 재구성하라는 뜻이 아니다. 기존 설치 위치를 우선한다.
- 작업 시작 전에 해당 저장소에서 `git worktree list --porcelain`로 등록된 작업 디렉터리와 체크아웃된 브랜치를 조사한다. 실제 작업 디렉터리에서 `git status --short --branch`와 `git status --porcelain`을 확인한다.
- 해당 브랜치의 상설 워크트리가 있으면 **그 디렉터리를 사용**한다. 없다면 기존 로컬 브랜치와 원격 추적 상태를 확인하고 상설 워크트리를 **최초 1회만** 만든다. 이미 체크아웃된 브랜치를 다른 워크트리에 중복 체크아웃하지 않는다.
- 작업 종료 후 `commit/push` 및 관련 검증을 수행하되 **워크트리를 그대로 유지**한다. 작업이 끝났다는 이유만으로 `git worktree remove`, `git worktree prune`, 디렉터리 삭제를 수행하지 않는다.
- `git clean -fdx`, `git reset --hard`, 강제 체크아웃, `git branch -D`, 강제 푸시, 미추적 파일·로컬 빌드 산출물 삭제 등 파괴적 정리는 **사용자 명시적 승인 없이 금지**한다.
- 미커밋·미추적 파일이 있으면 기존 작업으로 취급한다. 사용자가 요청하지 않은 `stash`, 자동 커밋, 덮어쓰기, 이전 작업 폐기를 하지 않는다. 충돌 또는 오염 위험이 있으면 중단하고 상태를 보고한다.
- 웹과 앱의 워크트리 및 빌드 디렉터리는 서로 독립적으로 관리한다. 앱의 CMake/Qt 빌드 산출물이 웹 소스나 다른 워크트리를 덮어쓰지 않도록 한다.

## 3. 작업 시작 및 `main` 동기화 방향

1. 저장소·작업 영역·기존 상설 워크트리를 식별한다.
2. 현재 브랜치와 원격 상태, `git worktree list --porcelain`, `git status --short --branch`를 검사한다. 미커밋 변경이 있으면 보존하고 사용자의 의도에 따라 처리한다.
3. `git fetch origin`으로 새 커밋을 가져온다. 필요 시 원격 작업 브랜치가 앞서 있는지도 확인한다.
4. **작업 브랜치가 `main`에 뒤처져 있으면 `main`의 변경사항을 작업 브랜치로 병합**한다. 병합 방향은 `main → work/*`이다. 보통 `git merge origin/main`을 사용하며, 충돌이 생기면 임의로 한쪽 내용을 버리지 않는다.
5. 해당 상설 워크트리에서 기능 구현·범위에 맞는 검사·커밋·푸시를 수행한다. 워크트리는 유지한다.

`main → work/*` 동기화는 `main`을 수정하는 행위가 아니다. **`work/* → main` 통합, `main` 직접 수정, 배포는 사용자 명시적 지시가 있을 때만** 수행한다. 사용자가 “최신 메인에 맞춰라”라고 지시하면 기본 해석은 전자다.

여러 `work/*` 브랜치 사이에 변경을 옮길 때에는 변경 목적·충돌·미완성 작업을 검토하고 사용자 승인 없이 무관한 영역을 통째로 합치지 않는다. 공유 브랜치 이력을 임의로 재작성하는 리베이스·강제 푸시도 금지한다.

## 4. 완료·병합·삭제 원칙

- 기능 완료는 테스트 및 결과 검증을 뜻하지만, **자동으로 `main` 병합하거나 상설 브랜치/워크트리를 삭제한다는 뜻이 아니다**.
- `main` 반영을 지시받았을 때는 diff, 관련 단위·UI·GIS/저장 계약 검사, 웹·앱별 영향 범위와 미완성 변경의 혼입 여부를 검토한다. 반영 방향을 PR의 base/head로 재확인한다.
- 상설 `work/*` 브랜치는 통합 후에도 재사용한다. 해당 브랜치에서 새 작업을 계속 이어간다.
- 예외적으로 생긴 임시 브랜치/워크트리도 **자동 삭제하지 않는다**. 미반영 커밋·변경 파일·관련 CI 참조를 확인하고 사용자가 삭제를 명시적으로 승인한 경우에만 정리한다.
- GitHub 원격 브랜치를 정리하더라도 로컬 워크트리는 별도로 존재한다. 원격 브랜치 삭제와 로컬 작업 디렉터리 삭제를 같은 작업으로 취급하지 않는다.

## 5. 문서의 적용과 변경

- `AGENTS.md`의 핵심 규칙을 작업 에이전트의 기본 동작 지침으로 사용한다. 이 문서는 세부 절차의 단일 출처다.
- 정책 변경 시 **웹·앱 각각 `main`과 존재하는 모든 `work/*` 브랜치**에 같은 개정 내용을 반영하고, 기존 `AGENTS.md`의 다른 개발 규칙을 훼손하지 않는다.
- 문서를 원격에 올린 것과 로컬 환경에 반영한 것은 별개다. 로컬 워크트리는 다음 fetch/merge 또는 pull 후 변경된 지침을 보게 된다.
- 저장소 보호 설정(GitHub Rulesets 등)이 없는 경우 문서는 기술적 푸시 차단 수단이 아니다. 보호 규칙이 필요하면 별도로 설정한다.
